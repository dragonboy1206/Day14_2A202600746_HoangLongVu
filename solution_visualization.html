Sơ đồ evaluation pipeline

Đây là luồng dữ liệu chính mà `BenchmarkRunner.run()` thực hiện khi chấm agent.

QAPair Chứa question, expected answer, context, metadata và retrieved_contexts.
Agent `agent_fn(question)` sinh ra actual answer để đem đi đánh giá.
RAGASEvaluator Tính faithfulness, relevance, completeness và retrieval metrics.
EvalResult Lưu điểm, pass/fail, failure_type và overall_score.
Report Tổng hợp pass rate, average scores và phân bố lỗi.
FailureAnalyzer Gom cụm lỗi, tìm root cause và tạo improvement log.

Các khối code đã hoàn thiện

Mỗi khối tương ứng với một phần quan trọng trong `solution/solution.py`.

Task 1

Data Models

`QAPair` và `EvalResult` là nền tảng để truyền dữ liệu qua pipeline.

  • `QAPair`: question, expected_answer, context, metadata, retrieved_contexts.
  • `EvalResult`: actual_answer, scores, passed, failure_type.
  • `overall_score()`: trung bình 3 metric answer-side.
Task 2

RAGASEvaluator

Chấm chất lượng answer bằng word-overlap heuristic.

  • `evaluate_faithfulness`: answer có grounded trong context không.
  • `evaluate_relevance`: answer có bám câu hỏi không.
  • `evaluate_completeness`: answer có cover expected answer không.
Task 2b

Retrieval Metrics

Chấm riêng bước get-context, chạy trên danh sách chunks.

  • `evaluate_context_recall`: union chunks phủ expected answer bao nhiêu.
  • `evaluate_context_precision`: Average Precision rank-aware.
  • `rerank_by_overlap`: đưa chunk liên quan lên trước.
Task 3

LLMJudge

Mô phỏng LLM-as-Judge bằng prompt rubric và JSON parsing.

  • `score_response`: gọi judge function, parse scores, fallback 0.5 nếu lỗi.
  • `detect_bias`: phát hiện positional, leniency, severity bias.
Task 4

BenchmarkRunner

Chạy toàn bộ QA pairs qua agent và tạo báo cáo aggregate.

  • `run`: agent answer -> evaluator -> EvalResult.
  • `generate_report`: total, pass_rate, avg scores, failure types.
  • `run_regression`: phát hiện drop lớn hơn 0.05.
Task 5

FailureAnalyzer

Biến điểm thấp thành insight có thể hành động.

  • `categorize_failures`: đếm lỗi theo type.
  • `find_root_cause`: suy luận nguyên nhân từ metric thấp nhất.
  • `generate_improvement_log`: xuất bảng Markdown tracking.

Năm metric chính

Ba metric đầu chấm answer, hai metric sau chấm retriever.

Faithfulness

Đo answer có dựa trên context hay đang bịa thông tin.

|answer ∩ context| / |answer|

Relevance

Đo answer có trả lời đúng trọng tâm question hay không.

|answer ∩ question| / |question|

Completeness

Đo answer có bao phủ đủ expected answer hay không.

|answer ∩ expected| / |expected|

Context Recall

Đo retrieved chunks có lấy đủ evidence cần thiết hay không.

|expected ∩ union(chunks)| / |expected|

Context Precision

Đo chunk liên quan có được xếp lên đầu danh sách retrieve không.

Average Precision@K

1. Data models: đóng gói dữ liệu đánh giá

`QAPair` là một test case trong golden dataset. `EvalResult` là kết quả sau khi agent trả lời và evaluator chấm điểm. Hai dataclass này giúp pipeline truyền dữ liệu rõ ràng thay vì dùng dict rời rạc.

QAPair.question Câu hỏi đầu vào của user, ví dụ: "What is RAG?"
expected_answer Đáp án chuẩn do người thiết kế benchmark viết.
retrieved_contexts Danh sách chunk theo thứ tự retriever trả về, dùng cho context recall/precision.
Ý tưởng chínhdataclass
QAPair -> agent_fn(question) -> actual_answer
EvalResult -> scores + passed + failure_type + overall_score()

2. Token hóa và overlap: nền tảng của metric heuristic

Vì bài lab không gọi LLM thật, các metric dùng word-overlap heuristic. Hàm `_tokenize` chuyển text thành tập token lowercase, bỏ punctuation và stopwords như "the", "is", "a".

Vì sao dùng set token?

Set giúp tính giao nhau nhanh: token nào xuất hiện cả trong answer và context thì được xem là overlap. Cách này đơn giản, deterministic, dễ test, nhưng yếu với synonym/paraphrase.

Vì sao cần `_overlap_score`?

Hàm này gom logic chia tỷ lệ và clamp điểm về 0-1. Nếu mẫu số rỗng, hàm trả 1.0 để tránh chia cho 0 và đúng với yêu cầu trong docstring của bài.

3. Answer metrics: chấm câu trả lời của agent

Ba metric này là phần answer-side của RAGAS-inspired evaluation. Chúng trả về float từ 0 đến 1.

Hàm Mục tiêu Khi điểm thấp
`evaluate_faithfulness` Answer có grounded trong context không Dễ có hallucination hoặc context thiếu evidence
`evaluate_relevance` Answer có bám sát question không Agent trả lời lệch ý hoặc prompt chưa rõ
`evaluate_completeness` Answer có phủ đủ expected answer không Answer thiếu ý quan trọng
Ví dụ tính completenessword overlap
answer   = "RAG combines retrieval with generation"
expected = "RAG stands for Retrieval Augmented Generation"

overlap tokens = {"rag", "retrieval", "generation"}
score = overlap / expected_tokens

4. Retrieval metrics: chấm bước get-context

Hai metric này không chấm answer, mà chấm danh sách chunk retriever lấy ra. Đây là điểm khác biệt quan trọng giữa lỗi do retrieval và lỗi do generation.

Context Recall thấp

Retriever không lấy đủ evidence. Rerank không sửa được vì chunk cần thiết chưa xuất hiện.

Context Precision thấp

Evidence có thể đã được lấy, nhưng bị xếp sau noise. Reranking sẽ giúp tăng điểm.

Average Precisionrank-aware
Chunk relevant nếu:
|chunk_tokens ∩ expected_tokens| / |expected_tokens| >= 0.1

Precision@k = relevant trong top-k / k
AP@K = trung bình Precision@k tại vị trí relevant

5. run_full_eval: nơi gom điểm và phân loại lỗi

Hàm này chạy đủ 3 answer metrics, quyết định pass/fail, rồi gán `failure_type`. Đây là trái tim của evaluator.

Pass

Khi faithfulness, relevance và completeness đều >= 0.5.

hallucination

Nếu fail và faithfulness < 0.3.

irrelevant

Nếu fail, faithfulness chưa quá thấp, nhưng relevance < 0.3.

incomplete

Nếu fail, hai metric trên không quá thấp, nhưng completeness < 0.3.

off_topic

Nếu fail nhưng không rơi vào ba ngưỡng cực thấp phía trên.

6. LLMJudge: mô phỏng judge theo rubric

`LLMJudge` nhận một hàm `judge_llm_fn`. Trong production, hàm này có thể gọi GPT/Claude. Trong test, nó là mock function trả JSON score.

`score_response` làm gì?
  • Tạo prompt gồm question, answer và rubric.
  • Gọi `judge_llm_fn(prompt)`.
  • Parse JSON score theo từng criterion.
  • Nếu parse lỗi, fallback score 0.5 cho từng criterion.
`detect_bias` kiểm tra gì?
  • Positional bias: câu trả lời ở vị trí đầu có thường cao hơn không.
  • Leniency bias: điểm trung bình quá cao, trên 0.8.
  • Severity bias: điểm trung bình quá thấp, dưới 0.3.

7. BenchmarkRunner: chạy toàn bộ golden dataset

Runner biến danh sách QA pairs thành danh sách EvalResult, rồi tạo report aggregate.

Luồng xử lýBenchmarkRunner.run
for pair in qa_pairs:
    answer = agent_fn(pair.question)
    result = evaluator.run_full_eval(answer, question, context, expected)
    if pair.retrieved_contexts:
        result.context_recall = evaluate_context_recall(...)
        result.context_precision = evaluate_context_precision(...)
    results.append(result)
`run_regression` dùng để làm gì?

Hàm này so sánh average metric của bản mới với baseline. Nếu metric mới giảm hơn 0.05, metric đó được đưa vào danh sách regressions và quality gate fail.

8. FailureAnalyzer: biến lỗi thành kế hoạch sửa

Đây là phần giúp bài lab không chỉ dừng ở "score thấp", mà đi tiếp tới root cause và action.

Hàm Vai trò
`categorize_failures` Đếm failure theo `failure_type` để thấy cụm lỗi lớn nhất.
`find_root_cause` Dựa trên metric thấp nhất để gợi ý nguyên nhân.
`generate_improvement_suggestions` Sinh danh sách hành động ưu tiên dựa trên pattern lỗi.
`generate_improvement_log` Xuất Markdown table để tracking failure và fix.
hallucination -> guardrail irrelevant -> prompt clarity incomplete -> context coverage off_topic -> routing check
